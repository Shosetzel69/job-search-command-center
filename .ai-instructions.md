### 1.1 Project sanity la reluarea chaturilor JSCC

- La primul mesaj substantiv din orice chat JSCC reluat, executa sanity **inainte** de a folosi starea istorica a conversatiei.
- Sanity este interaction-first: raporteaza mai intai ultima interactiune substantiva user↔assistant dinaintea triggerului, apoi ultima actiune materiala, subiectul, actualitatea si verdictul.
- Un trigger bare `sanity` nu este el insusi „ultima interactiune”; evalueaza schimbul substantiv imediat anterior.
- Actualitatea foloseste numai `DA / PARȚIAL / NU / ÎNCHIS`.
- Verdictul foloseste numai `CONTINUĂ AICI / MUTĂ ÎN ALT CHAT / POȚI ȘTERGE`.
- Outputul implicit ramane scurt; nu afisa DEV/TEST/PROD, SHA, release, blockers sau status general daca nu sunt necesare pentru a explica actualitatea chatului.
- `Schimbat între timp` apare numai daca exista o diferenta materiala relevanta.
- `POȚI ȘTERGE` este permis numai dupa ce orice informatie materiala existenta doar in chat este persistata.
- Daca starea GitHub nu poate fi verificata, raporteaza `SANITY — BLOCAT`; nu ghici.
- Sanity este read-only: nu deployeaza, nu modifica date/runtime/configuratie si nu atinge LEGACY.
- Formatul complet si contractul sunt definite in `docs/project-sanity.md`.

### 1.2 Trigger JSCC + URL pentru evaluarea surselor

- La orice mesaj al owner-ului care contine textul `JSCC` si cel putin un URL, consulta mai intai `docs/source-strategy.md` sectiunea **3.1 Evaluarea unei surse noi** inainte de a formula un verdict despre link.
- Daca URL-ul nu reprezinta o sursa candidata de joburi, spune explicit ca auditul de sursa nu se aplica si continua cu intentia reala a mesajului.
- Pentru o sursa candidata, aplica auditul complet din sectiunea 3.1; nu califica sursa din volumul total, pagina de prezentare sau eticheta generica `remote`.
- Cand acoperirea, regulile de acces sau continutul se pot schimba, verifica evidence extern curent inainte de verdict.
- Nu duplica aici criteriile de evaluare; `docs/source-strategy.md` ramane sursa canonica pentru ele.

## 2. Rolul AI si Niveluri de Autonomie

- Proiect **solo**: un singur developer cu rol de Architect/PM/Dev. Tu actionezi ca developer executant si consultant tehnic subordonat, nu ca decident.
- Nu presupune existenta unei echipe, a unui pipeline CI/CD complex sau a unor procese de aprobare multi-persoana.
- Nu iei decizii autonome de arhitectura sau de scop — poti propune, nu decizi.
- **Economie de context:** la modificarea codului existent, daca schimbarea afecteaza sub 30% din fisier, nu rescrie fisierul intreg — livreaza doar functiile/clasele afectate sau un diff. Cand furnizezi o modificare partiala, specifica intotdeauna calea fisierului, numele functiei/clasei afectate si liniile de context imediat inainte si dupa modificare, astfel incat ea sa poata fi aplicata exact, fara ambiguitate de pozitionare.
- **Regula de aur:** daca nu esti 100% sigur pe o cerinta, o regula de business sau o decizie de cod, intreaba. Nu face presupuneri — un modul rescris gresit din cauza unei ipoteze neconfirmate costa mai mult decat o clarificare prin text.

## 3. Guardrail pe etapele de lucru

Fluxul obligatoriu este definit in `GOVERNANCE.md`:

`Ideas / Requirements -> Analiza -> cerinta/decizie aprobata explicit -> Development -> implementare`

### Process routing

- Citeste campul `Process` din Issue-ul executabil.
- `AGENTFLOW` urmeaza `GOVERNANCE.md` + `docs/agentflow.md`; citeste `docs/agentflow.md` pentru executie AgentFlow si nu incepe implementarea fara `APPROVE_TASK_CONTRACT <reference>`.
- `LEGACY-ADAPTED` ramane pe procesul existent pana la inchidere; nu introduce retroactiv gate-uri AgentFlow fara aprobarea explicita a owner-ului.
- `INHERIT-PARENT` foloseste procesul declarat de parent/umbrella Issue; daca acesta nu poate fi determinat neechivoc, opreste executia.
- Un work item nu isi schimba procesul silent dupa inceperea lucrului.
- Pentru work item-uri active foloseste numai `Phase` si `Status` din taxonomia canonica `GOVERNANCE.md`.
- Nu emite ca status canonic `READY FOR DEV`, `WAITING FOR ...`, `READY FOR REVIEW`, `READY FOR TEST` sau `BLOCKED` simplu.
- Daca body-ul istoric contine un status vechi, nu il interpreta peste headerul canonic cel mai recent.
- Daca AgentFlow descopera un trigger material de arhitectura/scope/security/privacy/cost, foloseste statusul canonic de blocare al fazei curente si completeaza `Blocked by`; nu folosi `BLOCKED` singur si nu decide in DEV.

### Ideas / Requirements

Cand conversatia este in contextul `Ideas / Requirements`:

- nu scrii si nu modifici cod, indiferent cat de clara pare ideea;
- nu pregatesti implementare tehnica finala;
- nu creezi taskuri de Development;
- ajuti doar la explorare si maturizare;
- cand ideea devine suficient de matura, recomanzi explicit mutarea in `Analiza`;
- pregatesti un sumar scurt pentru transfer conform `GOVERNANCE.md`;
- nu redenumesti chatul.

### Analiza

Cand conversatia este in contextul `Analiza`:

- clarifici functionalitatea, impactul, scope-ul, alternativele si cerintele;
- nu scrii si nu modifici cod;
- nu tratezi rezultatul analizei drept aprobare de implementare;
- astepti aprobarea explicita a owner-ului pentru transfer in `Development`.

### Development

Codul poate fi scris sau modificat numai dupa ce owner-ul a aprobat explicit transferul cerintei in `Development`.

Daca nu este clar in ce etapa se afla cerinta, nu presupui ca este in Development.

## 4. Guardrails Tehnice

- Orice interfata sau contract marcat ca stabil/imuabil in `ARCHITECTURE.md` nu se modifica fara sa treci prin protocolul de schimbare (sectiunea 6) — indiferent cat de mica pare modificarea.
- **Implementation Preservation Rule:** aprobarea unei cerinte nu autorizeaza schimbarea mecanismului de implementare daca aceasta nu este ceruta explicit. Pastreaza component boundaries, responsabilitati, contracte/API, data flow, persistenta, autentificare, orchestrare, provider/runtime/framework, dependinte si algoritmi aprobati.
- Daca identifici o alternativa tehnica material diferita care pare mai buna, o propui separat ca change request. Nu o introduci in acelasi ticket fara analiza si aprobare explicita.
- **No Opportunistic Refactoring:** nu refactoriza cod adiacent, nu reorganiza componente si nu face redesign sau "cleanup" arhitectural doar pentru ca lucrezi deja in zona respectiva. Refactorizarea in afara scope-ului se trateaza separat.
- Daca un refactor este indispensabil pentru implementarea cerintei, explica necesitatea si impactul si obtine aprobarea inainte de modificare.
- Refactor permis direct doar pe o functie izolata, de maximum 50 de linii, fara sa-i schimbi semnatura (tip parametri/tip rezultat) si numai daca ramane in scope-ul aprobat.
- **Branch Target Safety:** inainte de orice write prin GitHub API verifica existenta branch-ului tinta si baseline-ul/SHA-ul; foloseste parametrul de branch explicit; `main` nu este tinta directa; daca branch-ul nu poate fi verificat, opreste operatia.
- Nu folosi niciodata `create_file`, `update_file`, `delete_file`, `update_ref` sau alta operatie de write pentru a testa daca un branch exista. Verificarea se face exclusiv prin operatii read-only.
- Dupa fiecare write, verifica branch-ul tinta si confirma ca `main` nu a fost modificat neintentionat.
- Nicio instalare sau adaugare de dependinte noi fara aprobare explicita — propune-le, cu argumente (dimensiune, licenta, motiv pentru care nu se poate scrie nativ).
- **Strict typing (TypeScript):** interzisa utilizarea tipului `any`. Foloseste tipuri explicite, generice, sau `unknown` insotit de type-guards.
- **Error handling:** niciun bloc `catch` gol sau care contine doar `console.log(e)`. Erorile se captureaza, se logheaza structurat si se impacheteaza in clase dedicate acolo unde arhitectura sistemului o cere.
- **Comentarii:** explica DE CE (motivul de business), nu CE face codul. Pentru logica cu reguli de business neevidente, explica regula in 2-3 randuri inaintea codului.
- **Stergeri de cod:** stergerea de fisiere, module sau eliminarea de functionalitati existente este interzisa fara aprobare explicita — se supune protocolului de schimbare (sectiunea 6), indiferent cat de „mort” sau neutilizat pare codul respectiv.

## 5. Security Guardrails

- Nicio cheie API, parola sau connection string hardcodat — exclusiv variabile de mediu (`process.env` sau echivalent), cu numele variabilei asteptate mentionat explicit.
- Daca ai nevoie de o cheie/secret pentru testare, cere sa fie setat local — nu genera una fictiva in cod „de test” care ar putea ramane acolo din greseala.
- Orice endpoint nou expus intern necesita autentificare, cu exceptia celor declarate explicit ca publice.
- Nicio trimitere reala de comunicari externe (email, notificari etc.) fara confirmarea ca fluxul a fost testat manual in prealabil.

## 6. Change / ADR Protocol

Cand identifici o nevoie de schimbare care depaseste guardrails-urile din sectiunea 4 sau care atinge o decizie de arhitectura conform `GOVERNANCE.md`:

1. **Nu scrii cod de implementare direct.**

2. Raspunzi mai intai in formatul:

```markdown
Problema: [descrierea scurta a problemei/nevoii]

Impact:
- [componente/module afectate]
- [riscuri de regresie]
- [impact asupra datelor/securitatii, daca exista]
- [complexitate estimata]

Optiuni:
1. [Optiunea 1]
   - Avantaje:
   - Dezavantaje:
2. [Optiunea 2]
   - Avantaje:
   - Dezavantaje:
3. [alte optiuni relevante, daca exista]

Recomandare:
[optiunea recomandata si motivatia tehnica]

Consecinte:
- [impact pozitiv]
- [trade-off-uri]
- [limitari introduse]
- [impact operational sau de mentenanta]

Solutie propusa:
[pasii tehnici exacti pentru implementarea optiunii recomandate]
```

3. Daca schimbarea tehnica propusa ar necesita cresterea versiunii majore a `ARCHITECTURE.md` (`v1.x -> v2.0`, `v2.x -> v3.0` etc.), anunti explicit utilizatorul **inainte de orice implementare**, mentionand:
   - de ce schimbarea este considerata majora;
   - ce limite arhitecturale sunt afectate;
   - ce impact are asupra componentelor existente;
   - ce versiune majora noua ar rezulta.

4. Astepti confirmarea explicita a utilizatorului.

5. Dupa aprobare, daca schimbarea necesita ADR, generezi draftul deciziei arhitecturale **inainte** de a scrie codul propriu-zis.

6. Numerotarea ADR nu se ghiceste:
   - verifici fisierele existente in `docs/adr/`;
   - identifici ultimul index alocat;
   - folosesti urmatorul numar secvential: `docs/adr/ADR-00(N+1)-titlu.md`.

7. ADR-ul trebuie sa documenteze minimum:
   - Context;
   - Problema;
   - Optiuni analizate;
   - Decizie;
   - Motivatie;
   - Consecinte;
   - Riscuri;
   - Impact asupra componentelor existente.

## 7. Testing + Definition of Done

- Cod nou = teste unitare/integration incluse, acoperind obligatoriu si cazurile de eroare, nu doar happy path.
- Testele automate de CI trebuie sa fie complet izolate — Mocks/Stubs pentru retea, baza de date sau servicii externe. Niciun test CI nu efectueaza apeluri HTTP reale sau nu depinde de disponibilitatea unei surse externe pentru a trece.
- **Claude web testing este o capabilitate suportata de QA:** pentru smoke/functional/E2E, Claude poate folosi browserul/web interaction atunci cand sesiunea concreta expune aceasta capabilitate si preflight-ul o confirma. Aceasta capabilitate este separata de Remote MCP GitHub.
- **QA/Testability UI Contract:** orice ticket/runbook QA care foloseste browser interaction include `docs/testing/qa-testability-ui-contract.md` in `Required context` si respecta contractul lui DOM-first.
- Fluxurile UI nominale DEV/TEST, inclusiv cleanup-ul fixture-urilor, nu trebuie sa depinda de `window.alert`, `window.confirm`, `window.prompt` sau alte dialoguri non-DOM necontrolabile portabil de executorul web.
- Daca un astfel de blocker apare neasteptat, marcheaza scenariul `BLOCKED-TESTABILITY`, colecteaza evidence si deschide/foloseste un defect dedicat; nu transforma blocker-ul accidental in `OWNER ACTION` si nu cere owner-ului sa faca click pentru a continua testarea automata.
- Un test web Claude poate cere navigare, click/select/input, citirea starii vizibile, Save controlat, reload, verificarea tranzitiilor UI si screenshot/evidence daca browserul le permite.
- Browser/web interaction NU implica automat DevTools/Network/Console, status HTTP exact, shell/CLI/Playwright, GitHub Actions sau Cloudflare. Acestea se declara separat si se folosesc numai daca preflight-ul confirma disponibilitatea.
- Pentru orice test, runbook sau ticket QA destinat lui Claude, include obligatoriu: `Executor`, `Environment`, `Required capabilities`, `Preflight`, `Authentication condition`, `Evidence`, `Capability fallback`, clasificare `PASS / FAIL / BLOCKED / N/A`, plus `Mutations / rollback` si `Owner gate` unde este cazul.
- Daca browserul este o capabilitate necesara si nu este disponibil in sesiunea concreta, scenariul este `BLOCKED`, nu `FAIL`. `FAIL` este permis numai pentru un comportament al produsului observat si contrar rezultatului asteptat.
- Daca Google login necesita interactiunea owner-ului, se marcheaza `OWNER ACTION`; AI nu cere credentiale sau token-uri. Dupa autentificare, testul continua in aceeasi sesiune daca browserul permite.
- Pentru PROD, defaultul este smoke/read-only. Orice mutatie permisa trebuie sa fie explicit definita, reversibila, cu baseline si rollback; esecul rollback-ului este `CRITICAL`. Full job search si alte actiuni cu impact operational necesita owner gate explicit.
- Nu cere Claude sa obtina secrete, token-uri sau workaround-uri neaprobate pentru a executa un test blocat. O asertiune HTTP/DevTools, CLI, Actions sau Cloudflare ramane `BLOCKED` sau se paseaza unui executor/canal care detine capabilitatea.
- Pentru upload catre servicii externe al CV-urilor, documentelor private sau altor date personale, testul necesita aprobarea explicita a owner-ului inainte de upload.
- Documentele de analiza sunt istoric de decizie, nu documentatie live. Dupa aprobare se actualizeaza doar statusul/outcome-ul si linkul catre decizia finala daca este util; nu se sincronizeaza continuu cu implementarea.
- Nicio functionalitate sau schimbare aprobata nu e „gata” fara:
  1. un entry in `CHANGELOG.md`, la sectiunea `[Unreleased]`;
  2. actualizarea documentatiei canonice material afectate de schimbare.
- Nu crea si nu actualiza documente fara impact material doar pentru a satisface procesul. Respecta `docs/documentation-policy.md`.
- Nu declari o functionalitate completa fara sa indici explicit cum se verifica (comanda de test sau pas manual concret).

## 8. Deploy Guardrail

- **Deploy Immutability Rule:** deploy-ul nu este o etapa de development si nu poate introduce modificari noi.
- Pentru PROD, fluxul este: `PR aprobat -> merge commit -> CI -> deploy exact al commitului/artefactului rezultat`.
- Nu aplica patch-uri locale, editari manuale sau modificari intermediare intre merge si deploy.
- Nu face deploy PROD dintr-o copie locala modificata.
- Daca apare o problema dupa merge, creeaza fix separat prin branch + PR; nu "repara la deploy".
- La finalul deploy-ului raporteaza commitul GitHub si, unde exista, Version ID / Build ID / deployment URL.

## 9. Output / Completion Protocol

- Orice Pull Request, Issue sau propunere de cod generata de tine include obligatoriu eticheta `ai-generated`.

### 9.1 Regula de lucru cu Issues

- La actualizarea unui Issue existent, pastreaza titlul si label-urile neschimbate implicit.
- Nu modifica titlul sau label-urile unui Issue decat daca owner-ul solicita sau aproba explicit acea modificare.
- O solicitare de actualizare a body-ului, de inchidere sau de redeschidere a Issue-ului nu autorizeaza implicit modificarea titlului sau a label-urilor.

- La finalul **fiecarui raspuns** in care ai generat sau modificat cod, incluzi obligatoriu:

```markdown
---
### Check-out Modificare
- **Fisiere afectate:** [lista fisierelor create/modificate]
- **Dependinte noi:** [Niciuna / denumire, daca au fost aprobate]
- **Eticheta PR:** `ai-generated`
- **Cum verifici:** [comanda exacta CLI pentru testul dedicat, sau pasul manual de validare]
```

- Un raspuns cu cod care nu include acest bloc e considerat incomplet.
